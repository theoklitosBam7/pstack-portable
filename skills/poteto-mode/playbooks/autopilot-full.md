### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names and PRs outside the authorized queue stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once per `../references/forge.md` and use that choice for every PR operation. One owner agent per PR, spawned through the harness with the `poteto-agent` persona and configured model role, owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip with `deslop` when that skill is installed, `/no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted in a location the root and a replacement can access, and return it with the reports. Whoever spawns a subagent records its ID, expected runtime (at least the longest past run of that kind), and state in a `children.tsv` in that location as soon as it starts. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, on a CI failure that comes from a change on trunk, or when a known concurrent change to the same files lands. When the shipped code is final, after the slop-strip and `/no-comments`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` pinned to the SHA it last pushed or took over. Check `ls-remote` first; if another push appeared, stop and report it to the root. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify the code-ready head.** Run one full swarm at the code-ready head. Run another full swarm only for new behavior, a redesign, or a large new diff. A rebase, conflict resolution, or minor fix gets one independent verifier at the new head. A wording-only change gets none. Apply the patch-id rule in `playbooks/shipping.md` to carried results, and require green CI on every new head. The full swarm reruns the gates, proves load-bearing behavior live on the real surface using a matching control skill or named driver, and audits the diff in two or more independent lanes with distinct focuses. Run a regression lane against trunk; if trunk lacks the feature, record that and gate the added behavior and the end state. Audit the merge-ready receipts before the verdict. The live lane is mandatory.

   Block only a demonstrated user-facing bug, failed gate, or wrong shipped documentation, supported by a failing run at the head or a doc line the PR made wrong. A defect already present on the base does not block unless the PR copies it or newly reaches it. Record other findings as follow-ups. Send blocking findings to a fresh owner with the accumulated brief; require a red test for each behavior defect or a repro receipt when a test cannot show it. Include the defect in the next review brief. A changed head gets a fresh verdict unless the patch-id rule carries the results. The root sends the owner the verdict and the head or patch it covers; the owner waits for that handoff before merging.
5. **The owner merges only what the root verified on the trunk it lands on.** Once verification lanes start, prepare the merge by rebasing onto current trunk, reporting the head, and waiting for green CI. Apply the patch-id rule in `playbooks/shipping.md` to the verdict. Before merging, fetch trunk and check whether its changes affect the patch. Rebase and wait for CI if the merge has conflicts, both sides changed a file, or trunk changed which checks run. If both sides changed a lockfile, a rebase is not needed when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. A failed install requires a rebase. If trunk changed a caller or dependency of the patch, run the patch's checks on the merge result before merging. If trunk would force a third rebase after merge prep, hold and ask the root to sequence the colliding work. The owner squash-merges through the resolved forge only after the root's clean verdict and green CI. A fresh owner takes the next item. Operator-named items and PRs outside the queue wait for the operator.
6. **Run the root layer.** Any change that loosens a gate, including a raised budget or allowlist entry, needs your fresh countersign, granted only after verifier proof. Remove a disabled or soft-failed check because it no longer guards every case. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. Use the harness's documented wake or scheduling operation. If the adapter has no timed wake, follow its documented fallback, such as tmux for a long local run, and state that hourly audits cannot be guaranteed. Never claim an unavailable cadence. At each tick, re-read this playbook from trunk with `git show origin/main:skills/poteto-mode/playbooks/autopilot-full.md` and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, cannot start a turn, or passes its expected runtime without a side effect as stuck. An owner with neither a push nor a trail row by the first tick is stuck. An agent waiting on the root or operator is not stuck; answer it. Stand it down and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners report where they stand and hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
